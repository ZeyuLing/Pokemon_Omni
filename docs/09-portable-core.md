# 可复用核心与 3D 开放世界接入契约

状态：整体架构与接口草案；战斗政策、合法性和安全入库已有共享 C99 实现，其他领域待实现，见 [最新实现范围](10-battle-policy-legality.md)。GBA 仍是首个必须交付的真实硬件版本，未来 3D 是同一游戏内容与规则的另一种表现。

## 1. 什么应当共享

| 领域 | 共享核心/内容 | 平台负责 |
|---|---|---|
| 剧情 | 章节、对白选择、条件、任务状态、奖励、分支后果 | 文本窗口/配音、镜头、动作和过场演出 |
| 人物 | 人物 ID、设定、阵营、关系、记忆、对话资格、训练师阵容、日程意图 | 像素角色/3D 模型、寻路、动画、表情、避障 |
| 世界 | 地区与地点身份、连通、通行条件、可交互对象、世界变化 | 2D 图块或 3D 地形、碰撞、导航网格、流式加载 |
| 宝可梦与养成 | 物种/形态、招式、特性、道具、成长、队伍、收藏、羁绊 | 精灵图/模型、音效、菜单和输入 |
| 战斗 | 合法性、行动顺序、命中、伤害、效果、形态、回合末与胜负 | 招式演出、血条动画、镜头和战场布局 |
| AI | 公开观察、推断、评估、合法动作生成与策略 | 配置计算预算、开发日志显示；不增加信息权限 |
| 保存 | 版本化逻辑状态、迁移与兼容检查 | flash、文件/云端 I/O、平台私有显示状态 |

GBA 的地图脚本和未来 3D 引擎脚本只做输入/展示桥接。可视化剧情编辑器可以存在，但导出同一声明式内容，不能各自维护另一套任务规则。

## 2. 依赖与实现方式

依赖方向是适配层 → 核心公共接口，核心不包含平台头文件。核心内部按域分模块，避免巨型全局对象；仅在真实边界使用接口，不构造占内存的通用对象框架。

拟定 C99 可移植子集，固定宽度整数、明确溢出边界、固定字节序的序列化，避免影响确定性的浮点计算、系统时间、指针顺序和未定义行为。不能因宿主是 64 位就让 `long` 大小进入游戏语义。平台可通过 C ABI 接入未来引擎，但具体 ABI、构建方式与 3D 引擎暂不冻结。

宿主提供受限内存 arena 和只读内容访问；GBA 采用静态/紧凑数据，主机可加载内容包。紧凑表内部索引与稳定领域 ID 的映射版本化，不能以编译排序改变存档含义。不要求跨平台布局相同，只要求公共语义和结果相同。

核心最低拆分：

```text
core/
  include/omni/     稳定领域 ID、命令、事件、只读视图和错误类型
  src/story/       任务、对白图、条件与一次性效果
  src/characters/ 人物身份、关系、日程与行为意图
  src/world/      地点图、访问条件、语义交互
  src/progression/队伍、成长、背包和收藏
  src/battle/     完整结算、规则和羁绊效果
  src/ai/         观察、信念、策略；不能旁路访问完整敌方状态
  src/save/       平台无关字段与迁移
adapters/
  gba/            RHH 桥接、显示、输入、保存、GBA 场景绑定
  headless/       无画面运行、记录和回放
  open_world_3d/  未来场景/物理/动画/UI 接入
content/
  characters/ quests/ dialogue/ world/ species/ text/
tools/
  content_compiler/ 语义校验与平台数据编译
```

这是预期布局，只对已需要的部分建立文件；当前目录中未出现的运行时代码均为未实现。

## 3. 命令、状态与事件

概念接口为：`dispatch(state, content, command, event_buffer) -> result`；每个入口明确容量、合法调用阶段和错误返回。所有修改经核心验证；平台不得通过可写视图改 HP、背包、任务或关系。

命令示例：与角色交互、选择对白选项、请求进入地点、选择战斗动作。事件示例：对白节点可展示、任务已推进、道具已获得、战斗请求已创建、伤害已结算、形态已改变。事件携带语义 ID 与结果，不携带 tile 坐标、指针、引擎节点或具体动画文件名。

核心在发出 `item_granted` 前已更新库存；前端只播放获得物品动画，不能收到事件后再加一次。多效果任务在一次领域事务内校验并提交，奖励使用稳定完成标记防重复。事件缓冲不足必须在提交前返回容量错误，或按明确可恢复分段协议处理；禁止状态已提交却丢失关键事件。

对外界面只暴露依观察者过滤的视图/事件。AI 只能得到公开观察；战斗完整内部状态只对结算器和受控调试记录可见。不能为了跨平台统一事件总线，反而把隐藏配招广播给 AI 或对手。

演出可以暂停展示队列，跳过动画不得改变结果。核心若已进入逻辑等待点，用唯一 continuation token 接收“继续”或“选择选项”；重复/过期确认无效，不把网络或动画回调当作奖励凭证。逻辑时钟由明确命令推进，不能根据 30/60/120 FPS 改变天气、任务条件或战斗顺序。

## 4. 可复用剧情与人物示例

已提供 [平台无关任务草案](../content/examples/partner-introduction.json) 和 [场景绑定草案](../adapters/examples/partner-introduction.bindings.json)。它们是接口讨论用的数据，不是已经能运行的脚本。

例子流程：到达研究所 → 与导师交谈 → 选择试炼 → 核心创建训练战 → 由核心确认胜利 → 一次性解锁伙伴任务。`interact_character` 由平台输入触发，`battle_finished` 只能由核心战斗域或受信任 legacy 桥接产生，不允许任意客户端提交“我赢了”。

同一个 `world.lab.entrance` 锚点在 GBA 绑定为地图/对象/格子，在 3D 绑定为场景/实体/触发区域。前端负责判断接近和碰撞；核心继续检查地点访问权限、人物交互资格和当前任务阶段。未来在线运行时，权威宿主还需验证空间事实，不能把客户端 `entered_anchor` 当作防作弊方案。

人物身份不能用当前精灵对象 slot 表示。人物状态如“已加入某阵营”“与玩家的信任程度”跨场景持久；走路路径、骨骼动作和模型朝向可由平台局部保存。核心可给出“前往港口等待”的行为意图，但不逐帧规划 3D 寻路。

任务条件采用受限、可静态检查的表达式和动作集合，如 `quest_state_is`、`relationship_at_least`、`has_item`、`request_battle`。不要把条件写成任意 GBA 脚本或 3D 引擎代码。为图的可达性、循环预算、对象引用、奖励幂等和取消/重入编写验证。

## 5. 战斗共享与 RHH 迁移

目标是同一套源码计算伤害与结算，不只是共用物种 JSON。上游引擎与全局状态/任务/动画的耦合程度需进一步审计；不能认为把它编译成库就完成解耦，也不能在没有测试基础时一次性重写全部机制。

采用逐域迁移：

1. 固定未修改 RHH 基线，记录代表性战斗、RNG/事件和结果，作为回归参考。
2. 新增剧情、人物、世界和羁绊长期关系优先在独立核心实现；GBA 场景通过桥接调用。
3. 战斗早期可以暂由 `legacy_rhh` 拥有完整状态。它只有适配接口，不标记为可移植实现；无画面假战斗也不能算结算复用证明。
4. 逐步抽离随机、规则数据访问、纯计算和效果解析，移除展示依赖，在主机与 GBA 执行同源测试。
5. 达到选定首发机制集的差分门槛后，单场战斗整体切换给共享核心；RHH 展示适配只消费结算事件。迁移期间逐个用例使用旧或新后端，禁止一场战斗两边共同写状态。
6. 若某机制未迁移，构建清单标注并阻止宣称其跨平台支持；生产内容扩张前完成首发战斗域迁移。

对比旧新后端时先规范化输入、规则版本和随机抽取序列，再比较结果；不同算法用同一个数值种子不保证等价。记录清晰的差异白名单，不能为通过测试吞掉错误。

3D 场景可以表现为无缝进入战斗，但只要规则仍为回合制，就使用同一结算器。如果将来增加自由瞄准、实时闪避和持续物理伤害，那是一个新的玩法模式，需要自己的规则与兼容声明，不能承诺只换渲染器就自动等价于 PvP 回合战。

## 6. 开放世界、性能与内容编译

3D 前端负责地形流送、LOD、物理、导航和可见性；共享核心只保留必要的逻辑地点、角色身份、世界变化与任务状态。卸载场景不能删除任务人物的长期关系，也不能重置已领奖状态。

内容编译器把同一剧情/人物/规则图编成 GBA 紧凑表与主机内容包。美术资源分别制作并以语义资产 ID 绑定，不承诺把像素图直接变成 3D 模型。Porymap 与 3D 编辑器各自拥有空间摆放，禁止反向覆盖共享剧情。

每个平台声明内容清单与支持能力，校验所有必须的语义锚点和替代演出。GBA 可以用文本/静态镜头表现同一事件，3D 用配音/镜头/动画；替代演出不得改变任务结果或奖励。

核心分配和计算预算由平台配置。AI 可使用不同 node budget，但信息权限和战斗规则不能因机器性能改变。确定性回放须记录 AI 参数/动作，不能要求不同思考预算自动选择相同动作。帧时间截止只可用于应急回退，离线可比实验采用固定工作量。

## 7. 存档与跨平台迁移

共享逻辑快照包含人物/伙伴稳定身份、任务/章节状态、背包、队伍、世界进度与必要随机状态，并携带核心协议、内容、规则和 ID 映射版本。编码不得直接写 C struct、地址、对象句柄或编译器 padding。

GBA 紧凑保存格式与主机格式可不同，通过显式导入/导出转成同一逻辑模型。平台私有区存镜头、图形选项或 3D 精确位置；跨平台旅行点优先以语义锚点转换，在 GBA 选择合法入口，不把坐标硬凑。

初期优先在无战斗、无未提交事务的安全点迁移。战斗中断续玩须额外保存动作阶段、待结算效果和 RNG，未实现前明确禁止跨平台迁移该状态。不得承诺任意 `.sav` 可直接在 3D 读取。

对目标端缺失的物种/任务/内容采取明确兼容策略：同版本完整支持则转换；否则拒绝或显式导出兼容子集并保留原档。未经定义的 3D 专属状态不得静默删除。双端进度合并不等于格式转换，需要另行设计冲突规则。

不强制把全事件历史存到 GBA。运行时使用短事件队列和紧凑快照；开发机才记录长回放。未来联网若采用服务端权威，同一核心可以部署在服务端，但协议、延迟处理和空间验证仍是新工作。

## 8. 最早期的验收门槛

- 核心用普通主机 C 编译器独立编译，不带 RHH/3D 引擎头文件；同时通过 ARM 目标构建。
- 一个共享任务在无画面宿主和 GBA 中经历相同命令，得到相同任务状态、关系与奖励，重入/跳过演出不重复发奖。
- 相同规则、内容、初态与动作/随机序列下，两端战斗语义事件与规范化状态摘要一致。
- 同一任务绑定到两个不同空间布局时无需修改剧情图；缺失锚点在构建阶段报错。
- GBA 内容表与主机内容包运行同一语义案例，验证编译不是两套逻辑翻译。
- 兼容存档往返转换保留逻辑状态；不兼容内容明确报错；快照大小、队列容量和真机耗时分别测量。

上述为后续实现的验收规范。本轮仅更新架构、目录职责和数据示例，不声称上述测试已经有可执行实现或已通过。
